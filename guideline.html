SOP Guideline

Update Sistem Pengajuan Kartu Garansi

Panduan ini digunakan saat melakukan update sistem lokal/static HTML yang terhubung ke Google Apps Script API. Fokusnya adalah memastikan perubahan frontend, backend, data Google Sheets, dan upload Google Drive tetap sinkron, aman, dan bisa di-rollback.

1. Arsitektur Sistem

Sistem ini bukan web app yang seluruh file HTML-nya di-host di Google Apps Script. Arsitektur yang dipakai adalah:

Frontend Lokal/Static

  • index.html
  • dashboard.html
  • guideline.html
  • config.js

File HTML dibuka langsung di browser atau didistribusikan sebagai file static.

Backend API

  • Code.gs
  • Google Apps Script Web App
  • Endpoint doPost dan doGet

Frontend memanggil backend melalui CONFIG.API_URL di config.js.

Data & File

  • Google Sheets
  • Google Drive
  • Trigger email digest

Data pengajuan tersimpan di Sheets, sedangkan file signed tersimpan di Drive.

Catatan CORS: frontend mengirim request dengan Content-Type: text/plain;charset=utf-8 agar request dari HTML lokal tidak memicu CORS preflight. Jika browser tetap memblokir request lintas origin, pertimbangkan opsi hosting/proxy yang mendukung CORS eksplisit.

2. Tujuan SOP

  • Memastikan update tidak langsung mengganggu data production.
  • Memastikan file frontend lokal/static dan backend Apps Script memakai environment yang sama.
  • Menjaga agar data pengajuan, file upload, dashboard admin, dan email digest tetap konsisten.
  • Mencegah kesalahan seperti meng-upload file HTML lokal ke Apps Script atau lupa mengganti CONFIG.API_URL.
  • Menyediakan langkah rollback untuk frontend dan backend secara terpisah.

3. Ruang Lingkup Update

Frontend Lokal/Static

  • index.html — form pengajuan, simpan draft, resume draft, dan submit final.
  • dashboard.html — dashboard Admin/Controller.
  • guideline.html — dokumen SOP lokal/static.
  • config.js — URL backend API dan konfigurasi frontend.

Backend Google Apps Script

  • Code.gs — endpoint API, validasi, business logic, Drive upload, dashboard API.
  • Google Sheets — struktur sheet dan data pengajuan.
  • Google Drive — folder file hard copy signed.
  • Trigger Apps Script — email digest dan proses terjadwal.

Penting: jangan menyamakan deploy frontend dan backend. Code.gs di-update di Apps Script, sedangkan file HTML tetap file lokal/static yang perlu diganti atau didistribusikan ke user.

4. Prinsip Best Practice

  1. Jangan update langsung ke production tanpa uji staging. Validasi frontend lokal/static dan backend API secara end-to-end.
  2. Backup sebelum deploy. Backup Google Sheet, kode Apps Script lama, dan salinan file frontend lama.
  3. Pastikan URL API benar. Cek CONFIG.API_URL sebelum smoke test, karena frontend bisa saja masih mengarah ke backend lama.
  4. Gunakan rollout bertahap. Uji dengan 1 cabang/admin lebih dulu sebelum dipakai semua user.
  5. Jalankan update saat jam sepi. Hindari update ketika user sedang aktif mengisi form atau upload file.
  6. Siapkan rollback. Frontend dan backend bisa di-rollback terpisah, tetapi harus tetap kompatibel API.

6. Prosedur Update di Staging

A. Backend Staging

  1. Buat atau copy project Google Apps Script untuk staging.
  2. Salin kode terbaru Code.gs ke Apps Script staging.
  3. Pastikan resource staging tidak memakai data production, terutama spreadsheet dan folder Drive.
  4. Jalankan setupApp() jika schema/config staging perlu dibuat atau diperbarui.
  5. Pastikan sheet Pengajuan memiliki kolom draft: Resume Token, Draft Created At, Draft Updated At, dan Submitted At.
  6. Deploy Apps Script staging sebagai Web App dengan akses sesuai kebutuhan test.
  7. Catat URL Web App staging.

B. Frontend Staging

  1. Gunakan file lokal/static dari repo: index.html, dashboard.html, guideline.html, dan config.js.
  2. Update CONFIG.API_URL di config.js agar mengarah ke URL Web App staging.
  3. Buka index.html langsung di browser.
  4. Buka dashboard.html langsung di browser.
  5. Jalankan pengujian flow utama dan edge case.

7. Verifikasi Flow Utama

A. Verifikasi Konektivitas

  1. Buka config.js dan pastikan CONFIG.API_URL mengarah ke environment yang sedang diuji.
  2. Buka index.html langsung di browser.
  3. Buka dashboard.html langsung di browser.
  4. Pastikan request frontend masuk ke Web App Apps Script yang benar.

B. Simpan Draft & Cetak

  1. Isi form lengkap tanpa upload file.
  2. Klik Simpan Draft & Cetak.
  3. Pastikan sistem menampilkan ID Pengajuan dan Kode Lanjutkan.
  4. Pastikan printout memuat ID Pengajuan.
  5. Pastikan row di sheet Pengajuan berstatus Menunggu Upload.

C. Lanjutkan Draft

  1. Reload halaman form lokal.
  2. Masukkan ID Pengajuan dan Kode Lanjutkan.
  3. Klik Muat Draft.
  4. Pastikan semua field dan item produk terisi kembali.

D. Submit Final

  1. Upload file hard copy signed dalam format PDF/JPG/PNG.
  2. Klik Submit Final.
  3. Pastikan row yang sama berubah dari Menunggu Upload menjadi Baru.
  4. Pastikan file tersimpan di Google Drive.
  5. Pastikan dashboard admin menampilkan pengajuan tersebut.

8. Verifikasi Edge Case

  • Masukkan token salah: sistem harus menolak draft.
  • Coba muat draft yang sudah final submit: sistem harus menolak.
  • Simpan ulang draft setelah mengubah item: data item tidak boleh duplikat di sheet PengajuanItems.
  • Upload file dengan format tidak valid: sistem harus menolak.
  • Upload file melebihi batas ukuran: sistem harus menolak.
  • Buka dashboard admin: status Menunggu Upload tidak boleh tampil.
  • Pastikan email digest tidak memasukkan draft berstatus Menunggu Upload.
  • Ganti CONFIG.API_URL ke environment salah pada staging test: test harus dianggap gagal karena frontend/backend tidak sinkron.

9. Prosedur Update Production

A. Backend Production

  1. Pastikan semua checklist staging sudah lulus.
  2. Backup kode Apps Script production, Google Sheet production, dan catat URL Web App aktif.
  3. Update Code.gs di project Google Apps Script production.
  4. Jalankan setupApp() satu kali bila schema perlu dipastikan.
  5. Deploy/update Web App production.
  6. Catat URL Web App production baru jika deployment menghasilkan URL baru.

B. Frontend Production

  1. Update atau distribusikan file lokal/static terbaru ke lokasi yang dipakai user.
  2. Sertakan file index.html, dashboard.html, guideline.html, dan config.js jika berubah.
  3. Pastikan CONFIG.API_URL di config.js mengarah ke backend production yang benar.
  4. Instruksikan user/admin membuka file HTML lokal/static yang sudah diperbarui.
  5. Lakukan smoke test production menggunakan satu pengajuan test.

11. Monitoring Setelah Release

  • Monitor 2–3 pengajuan pertama secara manual di Google Sheet.
  • Pastikan file upload masuk ke folder Drive yang benar.
  • Pastikan admin bisa membuka dashboard.html lokal dan login ke backend production.
  • Pastikan tidak ada draft yang masuk ke dashboard admin sebelum final submit.
  • Pastikan user/cabang memakai file frontend versi terbaru, bukan salinan lama.
  • Catat error yang muncul dari user/cabang selama hari pertama rollout.

12. Rollback Plan

Gunakan rollback jika form lokal tidak bisa submit, dashboard error, file upload gagal massal, atau data production terpengaruh.

Rollback Backend

  1. Kembalikan Code.gs ke versi backup sebelumnya.
  2. Deploy ulang Web App versi lama atau deployment sebelumnya.
  3. Jika URL Web App berubah kembali, catat URL lama yang harus dipakai frontend.
  4. Jangan hapus kolom baru dari Google Sheet sebelum memastikan tidak ada data penting di dalamnya.

Rollback Frontend

  1. Restore file frontend lokal/static versi sebelumnya.
  2. Pastikan file yang di-restore mencakup index.html, dashboard.html, guideline.html, dan config.js.
  3. Jika config.js sempat diubah, arahkan kembali ke URL Web App yang kompatibel.
  4. Validasi ulang flow lama: isi form, upload file, submit, dan cek dashboard.

Frontend dan backend bisa di-rollback terpisah, tetapi keduanya harus tetap kompatibel. Jangan biarkan frontend baru memanggil backend lama jika kontrak API sudah berubah.

13. Rekomendasi Rollout

Gunakan pendekatan parallel rollout: sistem baru dicoba oleh satu cabang/admin terlebih dahulu selama 1–2 hari. Pastikan mereka memakai file frontend lokal/static terbaru dan CONFIG.API_URL mengarah ke backend yang benar. Jika tidak ada masalah pada draft, resume, upload file, dan dashboard, barulah sistem dijadikan alur utama untuk semua user.

Kriteria Go-Live

  • Flow simpan draft, muat draft, dan submit final berhasil dari file HTML lokal/static.
  • CONFIG.API_URL sudah menunjuk ke Web App production yang benar.
  • Data tidak duplikat di PengajuanItems.
  • Draft tidak tampil di dashboard sebelum final submit.
  • Admin bisa memproses status setelah pengajuan menjadi Baru.
